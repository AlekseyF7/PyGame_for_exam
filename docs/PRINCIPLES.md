# Принципы и термины для защиты проекта

Короткая шпаргалка: что значит термин + как он реализован в игре «Jump or die».
Преподаватель может спросить любой из них — отвечаем своими словами + пример из кода.

---

## Принципы качества кода

### DRY — Don't Repeat Yourself («не повторяйся»)
Один и тот же код/значение не дублируется, а выносится в одно место.
- В проекте: все числа в `src/config/constants.py` (нет «магических чисел»);
  общий рендер предметов через словари спрайтов; общий метод `_item_on` в генераторе.

### KISS — Keep It Simple, Stupid («делай проще»)
Решение должно быть максимально простым, без лишнего усложнения.
- В проекте: HP врагов — просто счётчик попаданий; стрельба — таймер перезарядки;
  коллизии — обычные прямоугольники (AABB), а не сложная геометрия.

### YAGNI — You Aren't Gonna Need It («не делай впрок»)
Не пишем функционал «на будущее», пока он реально не нужен.
- В проекте: магазин скинов и доп. звуки осознанно отложены, чтобы не раздувать код.

### SOLID — 5 принципов ООП-дизайна
- **S — Single Responsibility (единственная ответственность):** у класса одна задача.
  Пример: `SaveService` только сохраняет/грузит, `LevelGenerator` только генерирует.
- **O — Open/Closed (открыт для расширения, закрыт для изменения):** новый враг/предмет
  добавляется новым классом-наследником, без правки старого кода.
- **L — Liskov Substitution (подстановка Лисков):** любого наследника `Enemy`
  можно использовать там, где ждут `Enemy` (все имеют `update`, `hit`).
- **I — Interface Segregation (разделение интерфейсов):** маленькие узкие интерфейсы
  (`Collectible.apply`, `Enemy.update`), а не один «толстый».
- **D — Dependency Inversion (инверсия зависимостей):** модель не зависит от pygame;
  в `GameModel`/`LevelGenerator` можно «подложить» свой `random.Random` (для тестов).

### Separation of Concerns (разделение ответственности)
Разные задачи живут в разных частях кода. В проекте — это и есть MVC (см. ниже).

## ООП — объектно-ориентированное программирование

Подход, где программа — это объекты с данными и поведением. 4 «кита»:

- **Инкапсуляция** — данные и логика спрятаны внутри объекта; снаружи — методы.
  Пример: состояние игры внутри `GameModel`, наружу — `update()`.
- **Наследование** — общий код в базовом классе, специфика — в наследниках.
  Пример: `Enemy → Zombie/Spider/Skeleton`, `Collectible → Coin/Elytra/Weapon`.
- **Полиморфизм** — один вызов работает по-разному для разных классов.
  Пример: `for enemy in enemies: enemy.update(dt, self)` — каждый враг ведёт себя по-своему.
- **Абстракция** — выделяем главное, прячем детали; абстрактные базовые классы
  (`ABC`, `@abstractmethod`) задают «контракт» (`Enemy.update`, `Collectible.apply`).

Вспомогательные инструменты ООП в проекте:
- **`@dataclass`** — класс только с данными (генерирует `__init__` и т.п.) — все сущности.
- **`Enum`** — перечисление фиксированных вариантов (`PlatformKind`, `WeaponKind`).

## MVC — Model-View-Controller (архитектура)

Разделение программы на три слоя:
- **Model (модель)** — данные и логика игры, **без pygame** (`src/models/`).
  Хранит состояние, считает физику, коллизии, счёт.
- **View (представление)** — только рисует то, что в модели (`src/views/`).
  Единственный слой, который трогает pygame и файлы ресурсов.
- **Controller (контроллер)** — игровой цикл, ввод с клавиатуры, смена сцен
  (`src/controllers/game_controller.py`); связывает Model и View.

Почему MVC: логику можно тестировать без графики, легко менять отрисовку, чистая структура.

## Игровые и алгоритмические термины

### AABB — Axis-Aligned Bounding Box
«Прямоугольник, выровненный по осям» — простейшая форма для проверки столкновений.
Два прямоугольника пересекаются, если они перекрываются и по X, и по Y.
- В проекте: класс `_AxisAlignedBox` (границы `left/right/top/bottom`) + метод `overlaps`.

### Game loop (игровой цикл)
Бесконечный цикл «обработать ввод → обновить модель → нарисовать кадр», ~60 раз/сек.
- В проекте: `GameController.run()`.

### dt (delta time) и независимость от FPS
`dt` — время одного кадра в секундах. Движение умножаем на `dt`
(`y += v * dt`), чтобы скорость не зависела от частоты кадров.

### Полу-неявный метод Эйлера (semi-implicit Euler)
Численное интегрирование физики: сначала обновляем скорость, потом по новой
скорости — позицию (`v += g*dt; y += v*dt`). Простой и устойчивый для игр.
- В проекте: `physics.integrate`.

### Процедурная генерация
Уровень создаётся алгоритмом «на лету», а не рисуется вручную.
- В проекте: `LevelGenerator` бесконечно досоздаёт платформы выше игрока.

### Детерминизм и seed
Если задать `random.Random(seed)`, генерация повторяется одинаково — это позволяет
писать стабильные тесты. В проекте генератор и модель принимают свой `rng`.

### Culling (отсечение)
Удаление объектов, ушедших за экран, чтобы не тратить память и время.
- В проекте: `_recycle_objects` убирает платформы/врагов ниже экрана.

### Broad phase (широкая фаза коллизий)
Перебор пар объектов для проверки столкновений (снаряды↔враги, враги↔игрок).
- В проекте: `_hit_enemies_with_projectiles`, `_check_enemy_contact`.

### Сложность алгоритма (Big-O)
Оценка, как растёт время работы при росте данных: `O(1)` — константа,
`O(n)` — линейно, `O(n²)` — квадратично. Перебор пар «снаряды×враги» — `O(n·m)`.

### Сериализация
Преобразование состояния в текст для сохранения (здесь — JSON).
- В проекте: `SaveService` хранит рекорд, монеты и громкость в `savegame.json`.
